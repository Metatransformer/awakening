# Design tests

A design test resolves one uncertain player-experience claim. It connects an
MDA hypothesis to observed behavior and a decision without turning current canon
into a diary.

Only one test is active during pre-production:
[RAID_LOOP_PROOF.md](RAID_LOOP_PROOF.md).

The earlier core-loop test was superseded by the base-defense pivot before human
testing. It has no pass or fail result; git history retains its plan.

Use [TEST_TEMPLATE.md](TEST_TEMPLATE.md) for future tests. Every test must name:

- the question and player-facing hypothesis;
- intended aesthetics and observable dynamics;
- the smallest authored test;
- the observation plan;
- criteria for pass, revise, stop, and invalid evidence;
- result, decision, canon changed, and follow-up.

Precommit the hypothesis and criteria before the first session. Once testing
starts, do not rewrite them to fit observations. Put raw notes, timecodes, and
player words in [../playtests/](../playtests/); put synthesis and the decision
in the test.

If the question changes materially, close the old test without inventing a
verdict and open a new one.
